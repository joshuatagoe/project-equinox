# Decisions

Key decisions, why we made them, and what they cost. A new decision is added in the same commit as the work it affects.

Status is **Accepted** (agreed with the user), **Proposed** (awaiting the user), or **Superseded** (replaced; the entry stays and points to its replacement).

D1–D10 were agreed in the 2026-10-10 Antigravity session that wrote `docs/prd.md`, `docs/architecture.md` and `user/users.md`; they are recorded here after the fact. D11 onward are logged as they happen.

## Decision log

| # | Decision | Why | Trade-off | Status |
|---|---|---|---|---|
| D1 | Python 3.12 in one local process: stdlib `http.server`, `decimal`, and `pydantic` for schemas. No queues, databases or services. | The brief says local deployment is fine and clarity beats infrastructure. The repo scaffold and both CI pipelines (`make gate`) are already Python 3.12. `decimal` gives exact money math in the standard library. | The brief notes the evaluators' stack is Go on GCP; we have to justify not using it. | Accepted |
| D2 | Four layers with one-way imports: models → adapters / engines → CLI and server. The matcher and router import only `models/`. | The brief requires separation between venue integration, normalization, matching and routing, and no venue assumptions in routing. Import direction makes that checkable. | More files and boundaries than a single script would need. | Accepted |
| D3 | All prices, quantities and fees are `Decimal`, never `float` or `int`. | Polymarket and Kalshi sizes can be fractional; float drift would make fee and cost comparisons wrong by fractions of a cent. | Every boundary has to convert strings to `Decimal` explicitly. | Accepted |
| D4 | Where a venue only quotes bids, the adapter derives the price to buy one side from the other side's bids (buy YES at 1.00 − best NO bid). | The router must see an ask ladder for every market without knowing which venue it came from. | Depends on the venue's book shape; see the research labels in D12. | Accepted |
| D5 | Fees are computed at each price level the order walks through and summed, not once on the average price. | The fee curve P×(1−P) is not a straight line, so fee-on-average-price is wrong when an order crosses several levels. | Slightly more code in the depth walker. | Accepted |
| D6 | Only venues that can fill 100% of the order compete on cost. If none can, the result is "insufficient liquidity" (CLI exit code 2) with each venue's partial fill shown. | Comparing a 40-contract partial fill with a 100-contract full fill on total cost picks the wrong venue. | No split routing across venues in the prototype. | Accepted |
| D7 | A venue whose total cost (price plus fees) is over the order's budget is disqualified. If all are, the result is "budget exceeded" (exit code 3). | The order request carries a budget; it has to be enforced. | — | Accepted |
| D8 | Two markets are equivalent only if holding YES on one pays out under exactly the same real-world conditions as holding YES on the other. | The brief asks us to define equivalence and justify it; this definition is strict enough to refuse "25 bps cut" vs "50 bps cut". | Strictness refuses some pairs a human would call "close enough". | Accepted |
| D9 | Tests run offline against JSON fixtures; `make gate` (ruff, then pytest) is the one check, the same in GitHub and GitLab CI. | Deterministic CI with no network flakiness or rate limits. | Fixtures can drift from the live APIs; see D12. | Accepted |
| D10 | Architecture contracts are settled before the work is split into feature PRDs for parallel agents. | Agents building adapters, matcher and router at once need fixed shapes to build against. | Planning time before any code. | Accepted |
| D11 | The router supports buying YES or NO. Each canonical market holds one order book per outcome, and the adapter builds both. | The review found that one book per market leaves NO orders undefined; the user chose to support both (2026-10-10). | Adapters must build two ladders; fixtures need both sides. | Accepted |
| D12 | Venue facts (fee formulas, rounding, API field names, book sort order, Fed market structure) are researched and labelled CONFIRMED / SECONDARY / UNCONFIRMED before fixtures are written. Results: `docs/research/venue_facts.md`. | `docs/architectural_review.md` states these facts without sources. | A research pass before writing code. | Accepted |
| D13 | One fee formula for every venue: fee = coefficient × contracts × (p × (1 − p))^exponent, summed per price level, then rounded up once per order to the venue's rounding step. Kalshi: coefficient 0.07 × series multiplier, step $0.01. Polymarket: coefficient is the market's `feeSchedule.rate` (0 if `feesEnabled` is false), step $0.00001. The fixed-per-contract and percentage fee types are dropped. | Both venues use this curve (venue_facts K9, P7), and no venue uses the other types. Kalshi's per-order rebate makes the total converge to one rounding per order (K10). For Polymarket, per-fill versus per-order rounding differs by at most $0.00001 per level. | Kalshi direct-member accounts pay up to 1¢ less than we show (A3). | Accepted |
| D14 | Each canonical market holds `books: {"YES": …, "NO": …}`, with asks sorted best-first by the adapter. Kalshi builds each side's asks from the other side's bids at 1 − p. Polymarket uses each token's own asks and never adds the mirrored bids. | Implements D11. Both venues list the best price last, and Polymarket's spec gets the order wrong (K4, P4). Polymarket's two books are the same liquidity shown twice (P5). | — | Accepted |
| D15 | Equivalence is decided on structured contract terms, not title similarity. Adapters extract terms (subject, event date, condition such as "change = −25 bps") from venue fields (Kalshi `custom_strike`, Polymarket `groupItemTitle`). The matcher compares terms. Title similarity only finds candidates, and a pair without terms can reach AMBIGUOUS at most. The router routes EQUIVALENT pairs only. The prototype parses one event family: Fed rate decisions. | The spec's title scorer gave a true pair 0.419 and false pairs ≥ 0.867 (AI_USAGE 2–4). Both venues publish structured terms for Fed markets (K8, P6). | Other event families can't be EQUIVALENT until someone writes a term parser for them. | Accepted |
| D16 | Router contract: `simulate(order, cluster, now) -> EquinoxTrace`. The trace has a `status` (ROUTED, NO_EQUIVALENT_MARKETS, INSUFFICIENT_LIQUIDITY, BUDGET_EXCEEDED, INVALID_INPUT) that maps one-to-one to CLI exit codes 0–4. It also has one quote per venue and the cluster's match results and risk flags. If no venue fills 100%, the status is INSUFFICIENT_LIQUIDITY. If some do but all are over budget, it is BUDGET_EXCEEDED. A venue with no depth is shown but can't win. | The architecture's contract could not tell exit 2 from 3, and the router never saw the match results it had to report (AI_USAGE 5). | — | Superseded by D27, which adds MARKET_NOT_FOUND and NO_ELIGIBLE_VENUE and renumbers the exit codes |
| D17 | Every market records `data_source` (live or fixture) and `captured_at_utc`. The trace warns FIXTURE_DATA, and STALE_DATA when a book is more than 300 s old at simulation time. If live fetching fails, the app uses fixtures and shows that warning. Fixtures are raw API responses, unedited, kept in `src/equinox/fixtures/` because the running app reads them. | The architecture's silent fallback would show test data as if it were live. | — | Accepted |
| D18 | Resolution sources are compared by institution (web domain), not by exact text. Remaining rule differences, such as how each venue treats a move that isn't a multiple of 25 bps, become risk flags in the trace. | Kalshi lists `federalreserve.gov` and Polymarket lists `federalreserve.gov/monetarypolicy/fomccalendars.htm` for the same FOMC statement (K7, P6); a text comparison would flag a false difference. | — | Accepted |
| D19 | Build lanes: feat-01 (models, fixtures, and a golden file of expected canonical markets) first and alone. Then feat-02a/02b (Kalshi and Polymarket adapters), feat-03 (matcher) and feat-04 (router) in parallel, each owning its own folder and test file. Matcher and router tests read the golden file, not adapter output. Then feat-05 (CLI), then feat-06 (the written deliverables the brief asks for: setup, architecture overview, equivalence and routing explanations, AI usage). | Parallel lanes need fixed inputs. The golden file removes the matcher's and router's dependence on the adapters. The brief's written deliverables had no owner. | The golden file must be updated if the adapters' output changes. | Accepted |
| D20 | Two markets whose structured terms are equal on the venues' own grid are EQUIVALENT, and any remaining difference in rules goes into the trace as a risk flag. Example: Kalshi "Cut 25bps" and Polymarket "25 bps decrease" are equal for every move in 25 bp steps. They differ only in how each venue treats a move that isn't a multiple of 25: Polymarket rounds it up to the nearest 25, and Kalshi's rule for it is not specified. | Classing these pairs AMBIGUOUS, the literal reading of D8, would mean no Fed pair is ever routed. The difference only matters for a move that isn't a multiple of 25 bps; the flag keeps it visible to the risk auditor. | The router may route a pair that pays differently in that rare case; the trace says so. | Accepted |
| D21 | No `/api/v1/*` HTTP endpoints. The CLI gets a `--json` flag that prints the full trace. The existing status server keeps `/health`. | The brief asks for a working prototype, not an API. `--json` serves the automated-client user with less code to build and test. | No network API for other programs; adding one later would be a thin wrapper over the same functions. | Accepted |
| D22 | Contract terms have one venue-neutral shape: **measure** (what number, e.g. "Fed upper-bound change, bps" or "AAPL price, USD"), **measured by** (e.g. "FOMC statement", "Pyth regular-session close"), **observed at** (date or instant, UTC), **comparison** (`gt`, `ge`, `lt`, `le`, `eq`, `between`), **threshold** (plus an upper bound for `between`) and **unit**. The Fed outcomes and stock strikes both fit: Kalshi "Cut 25bps" is "change `eq` −25 bps". | The Meridian fit check showed that terms shaped around the Fed family could not express "AAPL closes at or above $330". Kalshi's own `strike_type` uses the same set of comparisons (S2). | Adapters must map each venue's wording onto a fixed vocabulary for measures and methods. | Accepted |
| D23 | Equivalence rules, one per field, extending D20. Measure, observation time, threshold, unit or direction differ → DISTINCT. Only the strictness differs (`gt` vs `ge`), or only the venues' fallback procedures differ (holds, overrides, holidays) → EQUIVALENT with a risk flag. "Measured by" differs → AMBIGUOUS, which is never routed. | The strictness difference only matters when the value lands exactly on the strike; a different measuring method can change the payout on an ordinary day. | Rules are written per field rather than as one score, and every rule needs a labelled test pair. | Accepted |
| D24 | Every market records its **collateral**: asset name and whether it has monetary value. A venue settling in money with no value (Meridian's devnet USDC) is simulated and shown, but can't win, with reason TEST_MONEY. A1's USD = USDC parity applies only to collateral with value. | Without this, A1 silently treats devnet play money as dollars. | A test-money venue never wins a routing decision. | Accepted |
| D25 | Every market has a **tradable** flag set by its adapter: Kalshi `status: active`; Polymarket `active && !closed && acceptingOrders`; Meridian, inside trading hours and not paused. A market that isn't tradable is shown but can't win, with reason NOT_TRADABLE. | Polymarket markets keep trading after `endDate` (P3), and Meridian works out open/closed from the clock (Meridian ARCHITECTURE §4). Expiry dates alone can't answer "can I trade this now". | — | Accepted |
| D26 | Meridian is **not integrated**. Architecture §9 checks that a venue like it would fit without changes to the matcher or router: a mapping on paper (§9.1), plus hand-built Meridian-style markets in the golden test data that go through the real matcher and router (E7–E10, feat-04 tests 7–9). The Polymarket adapter gets no stock-market parser: without Meridian, those markets have no partner, because Kalshi has none (S1). | The user's goal (2026-10-10): make sure the system is robust enough that a market like Meridian could be integrated, not integrate it. A check counts only if it runs, so the fit check lives in the test suite. | The Meridian side is hand-built. A real integration would still need an adapter and a fixture. | Accepted |
| D27 | Statuses and exit codes: ROUTED 0, MARKET_NOT_FOUND 1, INSUFFICIENT_LIQUIDITY 2, BUDGET_EXCEEDED 3, INVALID_INPUT 4, NO_ELIGIBLE_VENUE 5. A cluster with only one market is routed to that market if it qualifies. | The order names a market, so "no equivalent markets" is no longer a failure: one venue can still be evaluated and explained. Every venue being excluded for test money or not trading needed its own outcome. | Exit code 1 changes meaning from the PRD's "no equivalent markets found". | Accepted |
| D28 | The events to read are listed in `src/equinox/tracked_events.json` (per venue: event ID and family), not discovered. | Polymarket event slugs carry a random suffix, and same-title duplicates exist (P6). Discovering them reliably is research of its own. | Live runs need new IDs after each event resolves. | Superseded by D47 |
| D29 | Every venue response is parsed with `json.loads(..., parse_float=Decimal)`. | Polymarket sends `feeSchedule.rate` as the JSON number 0.05, which becomes an imprecise float otherwise. | — | Accepted |
| D30 | The trace uses typed sections (order, cluster, quotes, decision, rationale, warnings) instead of the first version's generic "spans". | Each section can be asserted in tests and read without walking a span tree. The reviewer liked the span idea for auditability; typed sections keep the same content. | It is not OpenTelemetry-shaped. | Accepted |
| D31 | One gate script, `scripts/gate.py` (ruff check, ruff format --check, pytest), run with the project's venv interpreter. `make gate` and both CIs call it; Windows calls it directly. | `make` isn't installed on the Windows machine (it exited 127), and the Makefile pointed at `.venv/bin`, which doesn't exist on Windows. One script keeps the local check and the CI check identical (OpenEMR report: the local gate belongs with the CI job). | Windows setup uses `uv` to get Python 3.12. | Accepted |
| D32 | Nothing is deployed. The M0 equivalent of "deploy" is both CIs passing on the merge or pull request. | The brief accepts local deployment, and Equinox is a CLI with nothing to host. | No hosted demo. | Accepted |

The file check makes "parallel agents share no files" something that runs. | Each worktree spends a few seconds creating a venv. | Accepted |
| D34 | Pushes go to two remotes with one explicit command each: `origin` (GitLab, labs.gauntletai.com) and `github` (GitHub). `make push-hosts` pushes the current branch to both. | The user's direction: the GitLab repo is the origin, and every push reaches both hosts. | — | Accepted |
| D35 | The status board is Notion, connected through the Notion MCP server in the project's `.mcp.json`. | D36 | No process experiment comparing one agent with parallel agents. The four lanes after feat-01 run in parallel straight away. | The user's choice (2026-10-10). | D37 | Every adapter takes a `clock` (architecture §5.1). An adapter whose venue puts no timestamp on a response (Kalshi) sets `captured_at` from it. Live runs pass `datetime.now(UTC)`. Fixture runs pass the snapshot's capture time from its `index.json`, which `FixtureFetcher.captured_at` exposes. | The `Fetcher` returns only JSON, so "when the response was read" meant the moment of a fixture run: Kalshi fixture markets would never show STALE_DATA while Polymarket's, timestamped by the books, would (AI_USAGE 9). The user chose the clock (2026-10-10). | One more constructor argument on every adapter. | Accepted |
| D38 | The architecture revision reaches `main` by a fast-forward, pushed to both remotes, before feat-01 branches. The user's choice (2026-10-10). | No merge request or pull request for the design revision. Both CIs still run on `main` (D32). | Accepted |
| D39 | The models enforce five rules beyond the first list in architecture §4.5, now added to it: no floats in exact fields (D3), no EQUIVALENT text match (D15), a quote is eligible exactly when it has no reasons, a trace has a decision exactly when it is ROUTED, and a cluster is never empty. `MatchResult.market_a` and `market_b` are market IDs, not markets. | Each rule turns an accepted decision into a check at construction, so a bug in a parallel lane fails where it happens instead of in another lane's test. IDs keep a trace readable: the cluster already carries the full markets. | Lanes must pass `Decimal`s or numeric strings, never floats, and must build quotes and traces that agree with their status, in tests too. | Accepted |
| D40 | GitHub Actions is the CI of record. It amends D32: "deploy" at M0 means the GitHub gate passing. `.gitlab-ci.yml` keeps the same job, but it runs only when a project runner is registered and the CI/CD variable `EQUINOX_GITLAB_RUNNER` is set. | labs.gauntletai.com gives fellows' projects no shared runners: GitLab pipeline #1 failed with `stuck_pending_no_matching_runners`, and #2 and #3 sat pending. A runner on this PC would rerun the same script and only work while the PC is on (OpenEMR report). The brief doesn't ask for CI. The user's choice (2026-10-10). | GitLab shows no pipeline status, and the evidence for "CI passed" is on GitHub. | Accepted |
| D41 | Adapters handle bad venue data in three ways. A market whose strike or bracket isn't one the family's parser knows is kept with terms None and a warning (architecture §5.2). A market that fails validation is skipped with a warning. A malformed event response (a missing series, settlement source or market list) skips that event with a warning, and the other events still load. Polymarket also skips a market whose resolution source has no URL host, since two blank sources would look like one institution (D18). Every warning is one line. | The architecture only said what happens to one bad market; without the event rule, one renamed field would crash the CLI with a KeyError instead of falling back. Keeping unparsed markets lets them reach the text fallback. | A venue's schema change shows up as warnings rather than a failed run, so warnings have to be read. | Accepted |
| D42 | Matcher details. The cluster key writes `observed_at` (UTC) only when a market states one and `upper` only for a range, and writes numbers without trailing zeros. A stated `observed_at` is part of the event: both stated and different → DISTINCT; stated by only one market → AMBIGUOUS. Risk flags go on EQUIVALENT pairs only, and read the same in either argument order. The text fallback compares only pairs where neither market has terms. A repeated `market_id` is refused. `equinox.matcher` exports `evaluate_pair`, `terms_key`, `build_clusters`, `cluster_for`, `text_match` and `text_matches`. | D23 lists observation time as an event field, but the first matcher compared only the date, so two closes at different times on one day would have been routed as one market (found by the feat-03 lane; the user chose to fix it, 2026-10-10). A market that doesn't state a time may observe at another, so that pair can't be called equivalent. | A venue that states its observation time can't be matched with one that doesn't until both state it. | Accepted |
| D43 | Router details. A venue counts as tradable real money when it has neither NOT_TRADABLE nor TEST_MONEY. With no eligible venue: none of those → NO_ELIGIBLE_VENUE; any of them full but over budget → BUDGET_EXCEEDED; otherwise INSUFFICIENT_LIQUIDITY. An empty book records EMPTY_BOOK and PARTIAL_FILL. A total equal to the budget is within it, and a book exactly `stale_after` old is fresh. The trace's assumptions say A1, A3 and A5 without venue names. `simulate()` writes quote warnings only; the CLI adds the adapters' warnings. | §7.2 states the statuses in prose, and each reading now has a test. The layering guard forbids venue names in router code, so the assumptions can't be copied from this file. | The trace's assumption text differs in wording from the Assumptions section below. | Accepted |
| D44 | CLI details. Bad arguments or settings (an unknown outcome, a missing quantity, a non-number) are INVALID_INPUT, exit 4, never argparse's own exit 2, which means INSUFFICIENT_LIQUIDITY. A live venue that raises FetchError is read again, whole, from the snapshot, with the snapshot's clock and a warning naming the venue. Every adapter warning goes into the trace, before the quote warnings. `match` lists AMBIGUOUS pairs from both the terms rules and the text fallback. | An exit code is the contract for automated callers (D16, D27), so a usage error must not look like a liquidity result. | `--help` still exits 0 through argparse. | Accepted |
| D45 | A web UI with three server-rendered pages, defined from `user/users.md`: Price an order and the Market board for Jordan, Why these match for Morgan (architecture §8.3). The pages call the CLI's own functions; there is no JSON API, so D21 stands. Snapshot data by default, live on request. | The brief rules out only a *production* UI, and Jordan's story ("tell me which venue gives me the best net price for my order, and explain why") is better met by a page than by terminal output. The user asked for it (2026-10-10). Rendering on the server keeps the UI from adding logic or disagreeing with the CLI. | Each page click reloads the page; there is no client-side interactivity. | Accepted |
| D46 | Every match result carries a confidence level and a reason, derived from its verdict and risk flags: High (EQUIVALENT, only edge-case rules differ), Medium (EQUIVALENT, but the payout can differ in one stated case: the grid, a tie rule or the resolution source), Low (AMBIGUOUS; title-only pairs also show their title score), none (DISTINCT). The level never changes a verdict or a routing decision. `users.md` now says this instead of "confidence scores". | Morgan's story asks for explicit confidence. A numeric score as the basis for matching was rejected (D15, AI_USAGE 2–4), so the level describes how sure a rule-based verdict is rather than deciding it. The user agreed (2026-10-10). | Levels are coarse: two Medium pairs can differ in how often their caveat bites. | Accepted |
| D47 | Each adapter discovers the events of the families it can read. Fed decisions: Kalshi by series (`/events?series_ticker=KXFEDDECISION&status=open`, K13); Polymarket by the tag `fed-rates`, keeping only open, neg-risk events titled "Fed Decision in …?" (P12). `tracked_events.json` becomes the pinned fallback: it is used when a snapshot was captured before discovery existed, or when a live discovery request fails, and then the events and books still come from the live API. | Hand-picking one event (D28) meant Equinox never found an equivalent market; it confirmed a pair chosen for it, which misses the brief's question "whether market equivalence can be programmatically inferred". The user's direction (2026-10-11). | Discovery rules are written per family and per venue; a venue that renames its series or tag needs a code change. | Accepted |
| D48 | A regenerable catalog of every open market on both venues, written by `python -m equinox catalog refresh` to `.cache/equinox/` (gitignored) and never committed. This amends D1's "nothing is stored": a cache can be deleted and rebuilt at any time. A failed refresh keeps the previous catalog. | Reading every open market takes about 290 requests and 1.9 GB (K12, P11): too slow for each command or page load, and too large to commit as a fixture. | The catalog is as old as its last refresh, and a refresh needs a few minutes and enough memory. | Accepted |
| D49 | Markets load in three tiers. The **catalog** holds every open market as a lean entry: title, dates, best YES and NO ask, terms where a parser exists. **Families** are the discovered events, loaded as canonical markets from their listings. **Books** are fetched only for the markets being priced, and for the cross-venue groups shown on the board. `CanonicalMarket.books` becomes optional, with `best_asks` taken from the listing (K12, P11); the router refuses a market without books. | Books for every market would be hundreds of thousands of requests, and routing only ever needs one group at a time. | The model no longer guarantees books on every market; the router's boundary check does instead. | Accepted |
| D50 | Title-only candidates are found with an inverted index of informative title words, blocked by close date (within a few days) and requiring at least two shared informative words, then decided by the §6.3 fallback and its vetoes. A title match is still never EQUIVALENT (D15). | Comparing 133,002 Kalshi markets with 207,646 Polymarket Yes/No markets pair by pair is about 28 billion comparisons. | A true pair worded with no shared informative words, or dated days apart, is missed. | Accepted |
| D51 | Every snapshot folder under `src/equinox/fixtures/` is a data source (`--snapshot NAME`, and a selector in the web UI), alongside live. `snapshot-2026-10-10` stays the default and the frozen baseline for every existing test and README number. Newer snapshots also hold discovery responses and a small catalog sample. | Discovery needs fixtures that include the discovery requests, and fixtures are never edited (AGENTS.md), so new data comes as a new snapshot. | The default view still shows one meeting; the README points to the newer snapshot and live data. | Accepted |
| D52 | Readability is checked by the gate. Ruff's C901 rule caps function complexity at 10. `tests/test_quality.py` fails when a module under `src/equinox/` passes 300 lines or a function passes 40, when the web UI and the CLI import each other (both use `equinox.sources`), or when a path in the README's "Reading the code" table doesn't exist. | The brief evaluates "code readability, modularity, and documentation quality"; rules that run can't drift the way a style note can. | A limit sometimes forces a split a person wouldn't make; an exception needs its own decision entry. | Accepted |
| D53 | The catalog is saved as one SQLite file per refresh (`catalog-<UTC time>.sqlite` in `.cache/equinox/`), with tables for the markets, the matched pairs and the summary, and an FTS5 index on the titles. It is written under a temporary name and renamed when complete; older catalogs are then removed. SQLite and FTS5 are part of Python's standard library. This amends D1's "no databases" as D48 amended "nothing is stored": the file is a rebuildable cache, not a service. It replaces feat-09's planned `catalog-<time>.jsonl.gz`. | The All markets page searches and pages 287,523 markets on every request; a compressed JSON file would have to be read and parsed whole for each request. A new name per refresh means a refresh never overwrites a file that the web server has open, which Windows refuses. | A binary file instead of text; 110 MB on disk for the recorded refresh. | Accepted |
| D54 | Every catalog market gets one status. **Same bet:** its terms key (§6.2) equals that of a market on another venue; only these can be priced. **Unclear:** a title candidate (D50) the fallback calls AMBIGUOUS; the most similar one is kept, with its score and reasons, and it is never routed. **No match:** the rest. The title compared is the title plus the outcome label when the label adds words. A pair where both markets have terms is left to the terms. One veto is added for the catalog: two markets that each name an outcome the other's title never mentions ("Keria" and "Eddie" for the same MVP award) are DISTINCT. Markets already closed inside an open event are not listed; a market listed twice is kept once. | Some titles leave the outcome out ("Who will the next Pope be?", label "Pietro Parolin"). In the first live refresh, 25,517 of 34,807 unclear pairs (73%) named two different outcomes; with the veto the recorded refresh has 10,957. Grouping by terms key is the cluster rule the matcher already uses. | A same-bet pair is found only when the keys are equal, so a pair the pair rules would call AMBIGUOUS (a different measuring source, or only one stating an instant) shows as no match; the Fed family has neither. The label veto can miss a true pair whose labels name the same thing in different words. | Accepted |
| D55 | The live fetcher asks for gzip and unpacks it. The catalog refresh retries a timeout, a dropped connection, a 429 or a 5xx up to twice per request, waiting 2 s and then 4 s; any other error fails at once. The command line and the web UI don't retry: for them a failing venue falls back to the snapshot (D17). | With gzip the full catalog is 151 MB instead of 1.9 GB, and the recorded refresh took 158 s. The second live refresh failed on one TLS handshake timeout at Kalshi page 54, and without retries one dropped connection costs the whole download. | A refresh can take up to 6 s longer per failing request before it gives up. | Accepted |

## Assumptions

- **A1:** One USD on Kalshi equals one USDC on Polymarket, with no transfer cost or delay. Reason: the prototype compares venues, it does not move money. What it affects: cost comparison across venues.
- **A2:** Order books are frozen at the moment they were captured. Reason: books move in milliseconds and the simulation is not live. What it affects: every routing result; the trace records the capture time.
- **A3:** Kalshi fees are rounded up to the cent, as for FCM-cleared accounts. Reason: whether a kalshi.com retail account is a "direct member" with $0.0001 rounding is UNCONFIRMED (venue_facts K10); rounding to the cent never understates the cost. What it affects: Kalshi fees can be up to 1¢ per order higher than a direct member pays.
- **A4:** (Fit check only; nothing is built against it.) A venue like Meridian would expose HTTP endpoints like the other venues: `GET /api/markets?day=` and `GET /api/markets/{key}/book`, with prices in whole cents and quantities in whole contracts. Reason: the user's direction to assume Meridian has an API like Kalshi's and Polymarket's. What it affects: only the paper mapping in architecture §9.1.
- **A5:** Costs use list fees. Polymarket's taker rebates (up to 50%, paid daily) and builder fees are ignored. Reason: rebates depend on a trader's volume tier, which a single hypothetical order doesn't have. What it affects: Polymarket can be cheaper in practice than the trace shows.
