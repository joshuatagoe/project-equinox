# AI usage log

How AI was used on this project: tools, what worked, where it misled us, and how we corrected course. Entries are dated and added in the same commit as the work they describe. The brief asks for AI usage to be disclosed; this file is that disclosure.

## Tools

- **Antigravity agent session** — wrote `docs/prd.md`, ran an "architectural review" subagent (`docs/architectural_review.md`), wrote `docs/architecture.md`, `user/users.md`, and feature PRDs `docs/features/feat-01` to `feat-04`.
- **Claude Code (Claude Opus 5.5)** — reviewed those documents against the brief, ran the specified code, and ran research subagents for venue facts. In the implementation phase it wrote feat-01, feat-05 and feat-06 itself, and ran feat-02a, 02b, 03 and 04 as four parallel subagents, each in its own git worktree, then reviewed and merged their work. It kept the status board in Notion through the Notion MCP server.

**The product itself uses no AI.** Matching is rule-based on contract terms (D15), and routing is arithmetic on order books. AI was used to build Equinox, not inside it. An AI matcher was considered unnecessary for the one event family with structured terms, and too hard to explain for the families without them.

## 2026-10-10 — PRD, review and architecture (Antigravity)

### What worked
- **A separate reviewer pass on the PRD.** It raised integer contract sizes, bid-only order books, fee-on-average-price, partial-fill ranking and an unenforced budget. Those became D3–D7. Its facts about the venues were then checked (D12), and seven were wrong (item 6).

## 2026-10-10 — Resuming in Claude Code

### What worked
- **Four research subagents in parallel, each told to label every fact and to check the earlier claims rather than confirm them.** They returned sourced answers and raw API responses in about ten minutes, and found seven errors in the earlier review (item 6).

### Where AI misled us or we course-corrected
1. **The review said it audited "against the live APIs" but cites no sources.** Caught by reading `docs/architectural_review.md`: no URLs or quotes anywhere. Correction: D12, a research pass that labels each venue fact. Lesson: an unsourced "ground truth" is UNCONFIRMED until checked.
2. **The feat-03 numeric veto lets "25 bps" vs "50 bps" through when both titles name the year.** Caught by running the spec's code unchanged: "Will the Fed cut rates by 25 bps in December 2025?" vs the 50 bps version scored 0.946, EQUIVALENT, because "2025" counts as a shared number. Correction: D15 replaced title scoring with contract terms, and the title fallback ignores four-digit years and can never say EQUIVALENT. This pair is golden case E11, now DISTINCT. Lesson: run a spec's code on the cases it claims to handle before handing it to an implementer.
3. **The entity veto (Pennsylvania vs Michigan) is in the PRD but not in the feat-03 code.** Same script: "Will Trump win Pennsylvania in 2024?" vs the Michigan version scored 0.867, EQUIVALENT. Correction: the title fallback vetoes a differing US state or month (architecture §6.3). This pair is golden case E12, now DISTINCT.
4. **The matching thresholds were never tried on realistic titles.** A true pair worded the way the two venues word things ("…at the December 2025 FOMC meeting?" vs "Fed decreases interest rates after December 2025 meeting?") scored 0.419, DISTINCT, so the demo would find nothing to route. Correction: D15 decides equivalence from contract terms, which both venues publish for Fed markets, so true pairs are found without titles. On titles alone this pair (golden case E13) is now AMBIGUOUS, never EQUIVALENT.
5. **The architecture marked its interfaces "LOCKED" while they could not express two of the CLI's exit codes.** The trace had no status field to tell insufficient liquidity (exit 2) from budget exceeded (exit 3); the router never received the match results it was supposed to report; the review's finding about buying NO was not carried into the models. Correction: D11 (books for YES and NO), D16 and then D27 (one status per outcome, each with its own exit code), and a trace that carries the cluster's match results (D30).
6. **The review's venue facts were wrong in seven places.** Examples: it called macro markets fee-free on Polymarket (the Fed markets charge 0.05), described Kalshi Fed markets as cumulative thresholds (they are mutually exclusive buckets, or thresholds on the rate level), and gave Polymarket Fed markets a month-end close (their `endDate` falls on the decision day). Caught by the D12 research pass, which was asked to check these claims rather than confirm them. Correction: `docs/research/venue_facts.md`, which lists all seven. Lesson: in a research prompt, state an earlier claim as something to test.
7. **The AI widened "check that the architecture could handle Meridian" into building a Meridian adapter.** After the user said to assume Meridian has an API like the other venues, the plan gained a Meridian adapter lane, a synthetic Meridian fixture, a stock-market parser for Polymarket and CLI demo rows. The user corrected it: the goal is robustness to a venue like Meridian, not integration. Correction: D26. The check is now a paper mapping (architecture §9.1) plus hand-built test markets run through the real matcher and router, and the adapter, fixture, parser and demo rows are cut. Lesson: "make sure the system could handle X" asks for evidence that the design fits, not for X to be built.
8. **The AI pushed to the wrong host and skipped GitHub.** Asked to push, it sent the branch to `origin`, which pointed at origin.cursor.com and stalled on a credentials dialog. Then, after the user said the origin is labs.gauntletai.com, it pushed to GitLab only, although the README names both GitHub and GitLab. The user asked "did we also push to github?". Correction: D34, plus a remotes table in the README and AGENTS.md. Lesson: before any push, list the remotes and compare them with the hosts the project names.

## 2026-10-10 — Implementation in Claude Code

### What worked
- **Fixed shapes and frozen test data first.** feat-01 wrote the models and a golden file of 21 canonical markets before anything else, so four lanes could then run at once in separate worktrees with no shared files. Put together, the four passed the gate at the first try (217 tests).
- **A red run before every piece of code, plus deliberate mutations afterwards.** Breaking the code on purpose found tests that passed without the feature they claimed to check (items 11 and 12).
- **A grill before every commit.** Each one put the decisions an agent had made alone in front of the user, D37–D44 among them. One lane's report raised a gap against an accepted decision (D23), which was fixed before its commit (D42).
- **A live run against both public APIs** on 2026-10-10 loaded all ten markets and routed the running example the same way as the snapshot.

### Where AI misled us or we course-corrected
9. **The revised architecture made fixture data from Kalshi look fresh.** It set Kalshi's `captured_at` to "when the orderbook response was read", but a fixture fetcher reads the snapshot at the moment of the run, and the `Fetcher` contract returns only JSON, so the adapter couldn't learn the real capture time. Polymarket markets, timestamped by their books, would show STALE_DATA in the same run. Caught in the grill before seeding the board, by tracing feat-04 test 12 (STALE_DATA) back through the adapter contract. Correction: D37. Lesson: for each field a design fills from "now", ask what it holds in a fixture run.
10. **feat-04 pinned a test time that made every golden book stale.** Its injected `now`, 20:50:00Z, falls 328–349 s after the golden books were captured, past the 300 s threshold, so every golden quote would have carried STALE_DATA and test 12's 10-minute-old book would have tested nothing different. Caught while building the golden file in feat-01, by comparing the books' capture times with the PRD's `now`. Correction: `now` is 20:48:00Z (the user's choice, 2026-10-10). Lesson: check a pinned test time against the data's own timestamps and thresholds.
11. **Lane tests that were wrong before the code existed.** In feat-02b, PRD test 4 (fees) passed against an adapter that returned no markets, because it looped over an empty list. Caught at the red step, where it should have failed. Correction: it now requires the five markets first. In feat-04, a test for the runner-up's savings expected 0.482875 because it skipped the fee's round-up to $0.00001; the run failed, the code was right, and the test now expects 0.48288. Lesson: a red run where a test passes is a finding, not noise, and an expected number is worked out with the same rounding as the code.
12. **A CLI test passed with the feature removed.** feat-05's test for the live-failure fallback checked for a warning naming Polymarket and the snapshot, but the router's own FIXTURE_DATA line says both, so the test passed even when the CLI dropped the adapters' warnings. Caught by a mutation check before the commit. Correction: the test now requires the fallback notice itself ("live data unavailable"). Lesson: assert the words only the feature under test can produce.
13. **The running example claimed more than its numbers show.** Architecture §1 and the venue facts said that charging the fee on the average price "would pick the wrong venue" for the 5,000 NO order. Recomputed while writing ROUTING.md, the fee on the average price is $49.14, the same as level by level, so it changes nothing there; only ignoring depth flips the venue ($847.04 against $885.275). Correction: both documents and the README now say so, and ROUTING.md shows the fee effect with an order where it matters. Lesson: recompute each claim in a worked example, not just its totals.
14. **The AI treated "production UI is out of scope" as "no UI", then proposed one from the plumbing.** Asked how to open the feature, it said Equinox has no UI. When the user asked for one, it offered a choice between JSON routes and server-rendered HTML instead of starting from the users. The user corrected both: the brief excludes only a production UI, and the screens should come from `user/users.md`. Correction: D45, three pages derived from Jordan's and Morgan's stories. Later, asked whether the plan met the stories, the AI proposed rewriting Morgan's "confidence scores" requirement away; the user said "do not be lazy", and it was met instead (D46). Lesson: read an out-of-scope line for its exact words, design from the users first, and close a requirement gap rather than editing the requirement.
15. **A mutation check left stale bytecode behind.** In feat-07, mutating `max` to `min` and restoring the file in the same second kept the file's size and whole-second timestamp, so Python ran the mutated `.pyc` and a test failed on correct code. Caught because the restored code read correctly while the test still failed. Correction: the caches were cleared; CI builds from source, so committed code was never affected. Lesson: clear `__pycache__` after a mutation run.
16. **A commit went out with one file of the change.** Committing feat-07, the AI joined `git add` and `git commit` with `;`. The add failed on a path that was already staged for deletion, so nothing else was staged, and the commit that reached both remotes deleted the old status page while the server still read it, which broke `main`. Caught by checking the pushed commit's file list right after the push. Correction: a follow-up commit with the rest of the accepted change, not a rewrite of shared history. Lesson: chain staging and committing with `&&`, and check `git show --stat` before pushing.
17. **A measurement counted the same 100 events 400 times.** Measuring Polymarket's open events for the discovery plan, the AI paged the keyset endpoint with a guessed parameter (`next_cursor`). Polymarket ignored it and returned the first page each time, so the crawl reported 40,000 events and 496,800 markets. Caught by checking the crawl for duplicate IDs (100 unique). Correction: the parameter is `after_cursor` (venue fact P11), and the real count is 21,935 events. The first crawl of Kalshi's `/markets` also turned out to be 99.9% combo markets (K12). Lesson: check a crawl for duplicates and for what the items actually are before planning on its numbers.
18. **Listing markets read the clock once per market.** Splitting the Kalshi adapter into a listing and books on demand, the AI dated each listed market with its own clock reading. A frozen feat-02a test failed: it pins that the clock is read only as each order book arrives, which is when the prices were actually captured (D37). Correction: a listing is dated once per event, and `fetch_markets` passes a placeholder that each market's books replace at once. Lesson: a frozen test that fails after a refactor is reporting a changed meaning, not an obstacle.
19. **Ruff's cache hid an import-order error that CI would have failed on.** feat-09's tests were written before the modules they import existed, so ruff sorted those imports as third-party. Once the modules existed the order was wrong, but `ruff check` kept passing locally from its cache. Caught by running ruff with `--no-cache` while reviewing the tests. Correction: the imports were re-sorted, and `scripts/gate.py` now runs ruff without its cache, as CI does. Lesson: a local gate that can answer from a cache is not the same check as CI.
20. **feat-09's first tests stated counts the sample doesn't have.** They expected 553 Polymarket markets, every Kalshi market with an ask, and a venue filter that hides the other venue's titles. In the sample, 84 of those 553 markets are already closed inside events that are still open, so 469 are listed; three Kalshi markets quote 1.0000 on both sides, so nobody is selling and they have no ask; and a filtered row still names its match on the other venue. Caught at the first run against the code, before any test was approved or committed. Correction: the tests now state those facts, each with its reason. Lesson: count a fixture with the rule the code will apply, not with the rule assumed when planning.
21. **The architecture described the research crawls' pacing as Equinox's own.** It said requests are made 150 ms apart, but only the measurement scripts slept between requests; Equinox never has. Caught while updating §2 with the recorded refresh. Correction: §2 now says what the code does. Lesson: a number carried from a research script into the design needs the code that makes it true.
22. **The first model readings joined fields, misdated meetings and over-normalized.** The term reader's evals caught each in turn: the model quoted evidence as "title / outcome" (so every reading failed the evidence check), dated a two-day FOMC meeting by its first day, rewrote "cut >25 bps" as "le -50", used the market's close date as the event's date, and wrote the outcome into a numeric measure. None of these reached a decision: the checks rejected them or the pair stayed unclear. Correction: seven prompt versions, each scored on the gold sets, keeping the checks strict rather than loosening them. Lesson: a model reading is only as good as the check that can refuse it.
23. **A false same-bet found only in the live sample.** With zero false same-bets on the first gold sets, a 100-market sample of the live catalog read 8 IPO pairs as the same bet. Kalshi pays when an IPO is confirmed (the S-1 declared effective, priced, or a ticker assigned) and Polymarket when it is completed, by the first sale of shares. Caught by reading every model-read same bet in the sample against both venues' rules. Correction: the IPO pairs joined the gold set, the prompt now names a measure as narrowly as the rules define it, and all 19 IPO pairs read as different. Lesson: an eval set is evidence about the families in it; a sample of what the system actually meets has to be read too.
24. **The AI labelled two eval pairs wrong.** It labelled Kalshi's and Polymarket's "2+ touchdowns" props as the same bet. Kalshi counts every touchdown the player scores; Polymarket only rushing or receiving touchdowns. Caught when the model's readings named the measures differently and the full rules were read. Correction: both pairs are labelled different, with the reason in `evals/pairs.json`. Lesson: label from the full rules, not the first lines.
25. **A capture script saved parsed responses as a fixture.** Recording the Ballon d'Or pair for the pricing tests, the AI first wrote each response as re-serialized JSON, which turned the venues' numbers into strings: not the raw, unedited responses the fixtures must be. Caught while reviewing the saved files, before any test used them. Correction: the folder was deleted and `docs/research/capture_pair.py` now saves the response bytes as received. Lesson: a fixture is what the venue sent, not what the code parsed.
26. **Two tests passed before the code existed.** feat-11's first Polymarket test compared each venue's terms for equality, and its negative test expected no terms. With no parser, every market had no terms, so both passed: None equals None. Caught while recording each test's failure before writing the parser. Correction: the test asserts each market has terms before comparing their keys, and the negative test first shows the unedited market has terms. Lesson: a test that passes before the code is checking nothing; watch each one fail.
27. **The parser chosen by event broke a frozen rule.** To price a catalog score pair, the AI made both adapters pick the parser from the event itself, for every listing. A frozen feat-02a test requires an event tracked under a family with no parser to have no terms, and the full suite failed on it. Correction: the event decides only when it is loaded without a family, as for a catalog market (D65); a tracked family keeps its own parser or none. Lesson: run the whole suite, not only the new tests, before calling a slice done.
28. **A 30-pair sample was reported as "no false same-bet".** docs-01 said 30 random model-read same bets, checked by hand, had no false same-bet, which read as the model being reliable. The exact-score parser then let every one of the 456 score same bets be checked against the venues' own fields: 7 were false, all reversed scores. At 1.5%, a sample of 30 more likely than not shows none. Correction: the docs now give the full check's count, and feat-12 makes the false pairs gold traps. Lesson: when an exact source exists, check every pair against it; a small clean sample bounds nothing.
29. **The AI set a target before measuring the baseline.** feat-12's grill defined "the reader improved" as fewer raw false same-bets on the judging half than the baseline. The baseline then showed 0 there: on those groups the model's order mix-up shows as missed same bets, not false ones. Caught when the baseline was recorded, before any reader change. Correction: the user agreed a target that can move (traps 0 raw, fewer misses, no new false same-bet). Lesson: measure first, then define the target.
30. **The first score set had too few same bets to judge.** Keeping each match's first planned request gave the judging half 8 same bets in 1,400 pairs, because a request starts with the most similar titles, mostly different scores. Caught by the builder's own summary, before anything was recorded. Correction: keep the request with the most same bets per match (160 in 1,600 pairs, 80 a half). Lesson: print what a gold set contains before paying to score it.
31. **The fixture score set hid Kalshi's strike fields from the model and the checks.** Since feat-11 the score gold set built each market without its event title or strike fields, which every catalog read sends. So the score-order check couldn't check a Kalshi market in the eval, and in the first reader attempt a misread ("PSV wins 1-0" read as home 1, away 2) passed as a false same-bet that a live read would refuse. Caught by reading that false same-bet. Correction: the set shows markets as a catalog read does (D73). Lesson: an eval must give the model and the checks what production gives them.
32. **The AI called 157 markets "parser misses" before reading why the parser refused them.** The upkeep run's verdict said the parser missed every one, because the model read each as an exact score. Reading the descriptions showed a new Polymarket wording that counts extra time: a different bet, which the parser was right to refuse. Caught before anything was taught to the parser. Correction: the command tells the reader to check why the parser refused each, and a period for extra time is on the cut list (D74). Lesson: a model reading a market as a family doesn't make it the same bet.
33. **feat-10's pricing took each market's latest reading.** A market read in several requests gets named differently in each, so pricing mixed readings from two requests and refused 71 of 229 re-read same bets as "no longer matching". The feat-10 tests priced one pair read once, so they couldn't see it. Caught by pricing a re-read pair live (Taylor Swift, Person of the Year). Correction: pricing uses the most recent readings that agree (D75), tested with a later reading that names the market another way. Lesson: test with the data's real shape: a market read more than once.
34. **The AI said D76 would leave every frozen test alone.** It kept the tracked families' rule so the feat-02b test still held, and told the user no frozen test would change. Its own feat-11 test also pinned the catalog path (a score market whose event names no source is skipped), and the gate failed on it. Caught by the full suite before the commit. Correction: the user agreed to update that test to the new rule. Lesson: before promising a frozen test won't change, grep every test for the behaviour, not only the one you remember.
35. **Search results opened on a data source that couldn't price them.** The new search linked each same bet to the order page on the page's current data source. The catalog is read live, and a snapshot holds only the Fed meetings, so clicking a score gave "not in the snapshot snapshot-2026-10-11". The tests had built their catalog from the same snapshot they priced from, so they couldn't see it. Caught in the browser check. Correction: a result is priced from where the catalog was read (D78). Lesson: click through what you build; a test that shares the code's assumption can't catch it.
36. **The AI labelled a market with no match "Only on Kalshi".** Its All markets design said which venue lists a market that has no match. The browser check found the same question, word for word, on both venues: they date it a year apart, so the title index never compares them. Caught in the browser check, before the commit. Correction: the row says "No match found" and what was looked for (D84). Lesson: a label says what the system checked, not what its result seems to imply.
37. **The landing view put the least certain same bets first.** The listing kept the venues' order, so All markets opened on 229 model-read bets (Medium at most) and the Fed and score matches a parser decided came after them. The tests checked that only same bets were shown, not which came first. Caught in the browser check. Correction: a parser's matches come first (D82), with a test whose model-read pair is listed first by the venues. Lesson: the first screen is a claim about what matters most; test its order.
38. **Tests passed that a reader would not.** The new app passed its 18 tests, and the first browser check still found a decision number ("(D58)") in a confidence reason, the model's name in doubled brackets on every row, outcome names cut off on cards and a Contracts box wider than its panel at phone width. Caught in the browser check, at desktop and phone width. Correction: each thing said once, no decision numbers on pages, names that wrap, inputs that fit (D89). Lesson: tests check that the words are there; only reading the page checks how it reads.
39. **Half the new flow was unchecked.** The first mutation run left 7 of 15 mutants alive: search by the other venue's words, the order of events and outcomes, pricing from the catalog's own snapshot, marking rule differences, hiding decision numbers and refusing a bad budget. One test written to pin the likelihood rule passed under both rules, because the fixtures' likeliest outcome is the same either way. Caught by mutation checks before the commit. Correction: a test per survivor, each seen to fail on its mutant, and the likelihood test rebuilt around the live case (D88). Lesson: a test of a rule needs data where the rule and its rival disagree.
40. **The AI repeated entry 16.** Committing feat-14's first part, it joined `git add` and `git commit` with `;` again. The add failed on a test file already staged for deletion, and the commit held only the deleted files. Caught by `git show --stat` before anything was pushed. Correction: the unpushed commit was amended to hold the whole accepted change. Lesson: a lesson logged is not a habit; chain staging and committing with `&&` every time.
41. **Keeping the model's decisions took half a minute.** The tests kept one decision; a copy of the real catalog kept 6,363 in 19.6 s and recorded them in 32.7 s, during which the app would have shown no model-read bets. Profiling showed one query per market and one scan per pair, in code `catalog read` already used. Caught by timing the step on a real-size copy before the commit. Correction: each table is read once (0.1 s and 0.6 s on the real catalog), with no schema change (D91). Lesson: time a step on production-size data before calling it done.
42. **A test that passed until 09:00 UTC.** feat-14's "home says how old its prices are" fixed the app's clock at 09:00 UTC on 2026-10-12 but built its catalog at the real time. It passed in the morning, CI included; from 09:00 the catalog looked newer than the clock, the page said "-3000 seconds ago", and the test failed, so `main` would have failed its next CI run. Caught by the gate later that day. Correction: an age is never below zero, in the code; the frozen test is unchanged and now passes at any hour. Lesson: when a test pins one clock, check every other clock its data carries.
